================ دليل v64: التركيب والتحديثات والعميل الجديد ================

## أ) لصق الحزمة على جهازك (نفس العميل/نفس الإعدادات)
1. أغلق البرنامج (kill_old_server.bat).
2. انسخ نسخة احتياطية من مجلد البرنامج + lis.db + static/uploads (احتياط).
3. فك الزيب والصق محتوياته فوق مجلد البرنامج مع الاستبدال:
   app.py, auto_updater.py, cloud_sync.py, astm_host.py, database.py, ومجلد templates/ كله.
4. شغّل البرنامج. التحديثات التلقائية لقاعدة البيانات (أعمدة/جداول جديدة) تتم لحالها عند أول تشغيل.
5. افتح: لوحة المصمم ← 📦 حزمة الإعدادات للتأكد أن الصفحة تفتح.

## ب) إرسال البرنامج للعميل
- عميل جديد: ابنِ Setup من نافذة «نشر تحديث للعملاء» (الخطوة 4: تجهيز ملف تنصيب العميل) ثم نصّبه عنده.
- عميل عنده برنامج منصّب: الأفضل «ابنِ ووقّع وانشر» (تحديث داخل البرنامج) — لا يلمس lis.db ولا uploads ولا backups،
  ويأخذ نسخة من القاعدة قبل التحديث ويعزل التحديث التالف تلقائيًا. لا تعيد التنصيب إلا للضرورة.
- قبل أي إعادة تنصيب فوق نسخة فيها مرضى: خذ نسخة من lis.db و static/uploads وجرّب الـSetup على جهاز تجريبي أول.

## ج) ما يصل للعميل وما لا يصل (بعد الـSetup/التحديث)
| الشي | الكود والقوالب | الإعدادات والتصاميم والأطباء والشهادات |
| تحديث «ابنِ ووقّع وانشر» | نعم (لكل العملاء) | لا |
| Setup جديد | نعم | لا (القاعدة تبقى قاعدة العميل) |
| حزمة الإعدادات (زيب أو إرسال عن بُعد) | لا | نعم |
- التحديث المنشور يصل لكل عملائك (مجلد GitHub عام واحد) وليس لعميل واحد.
- الإعدادات (شهادات الأطباء، تصاميم التقارير والباركودات، الشعار، الألوان) تُرسل لعميل محدد بـ:
  لوحة المصمم ← 📦 حزمة الإعدادات ← القسم 3 (إرسال عن بُعد، يحتاج معرّف جهازه) أو القسم 1+2 (ملف zip تستورده عنده).

## د) عميل جديد — الخطوات كاملة
1. نصّب الـSetup + فعّل الترخيص كالمعتاد.
2. من جهازك: 📦 حزمة الإعدادات ← تصدير (فعّل «تضمين اسم المختبر…» لو تريد اسم/شعار هذا المختبر) ← استورد الملف عند العميل
   (نسخة جديدة بلا زيارات: يُستورد كل شي حتى الكتالوج والأطباء).
3. بوابة النتائج (Cloudflare) — لكل عميل Worker وقاعدة D1 ومفتاح خاص به:
   a) dash.cloudflare.com ← Storage & databases ← D1 SQL database ← Create ← اسم مثل lis-portal-<اسم-العميل>.
      ثم Console والصق محتوى portal_worker/schema.sql ونفّذ.
   b) Compute ← Workers & Pages ← Create ← Create Worker ← اسم مثل lis-portal-<اسم-العميل> ← Deploy.
   c) Edit code: الصق كود الـWorker نفسه (انسخه من Worker «lis-portal-hematology-lab-alkut» عندك أو من ملف src/index.js) ← Deploy.
   d) Settings ← Bindings ← Add ← D1 database ← Variable name: DB ← اختر قاعدة العميل.
   e) Settings ← Variables and Secrets ← Add ← Type: Secret ← Name: API_SECRET_KEY ← قيمة طويلة عشوائية (خزّنها).
      (اختياري) Variable: RETENTION_DAYS = 45.
   f) افتح https://<اسم-الworker>.<حسابك>.workers.dev/healthz — لازم يرد: lis-portal-ok
   g) ببرنامج العميل: الإعدادات ← بوابة النتائج:
      فعّل المزامنة، رابط البوابة = رابط الـWorker (بدون / بالنهاية)، المفتاح السري = قيمة API_SECRET_KEY،
      الوضع = remote (Cloudflare Worker)، احفظ.
   h) افتح ورقة QR لأي زيارة ← «دفع للبوابة الآن» ← لازم يظهر ✅. امسح الـQR بالموبايل للتأكيد.

## هـ) عميلك الحالي (عنده مرضى) — خطة آمنة بدون مسح بياناته
ملاحظة: صفحة «نشر تحديث للعملاء» (update_publisher.py) تبني وتنشر التحديث فقط؛ بناء LabSystem_Setup.exe يتم من «تجهيز ملف تنصيب العميل»
(client_builder.py) وما وصلني، فما أقدر أؤكد هل الـSetup يحافظ على lis.db عند مسح القديم.
الطريق الآمن (بدون إعادة تنصيب):
 1) عندك: الصق v64، شغّل، وتأكد من الأقسام (الطباعة، الباركود، التقارير، البوابة).
 2) 📦 حزمة الإعدادات ← تصدير: فعّل الكل + «تضمين اسم المختبر…» + «تضمين الصور» (يحمل: اسم/هاتف/عنوان المختبر، الشعار، تصاميم التقارير
    والباركودات، أطباء المختبر وشهاداتهم، الأختام والتواقيع، تصاميم التقارير لكل تحليل). احفظ ملف zip.
 3) انشر التحديث: نافذة «نشر تحديث للعملاء» ← «ابنِ ووقّع وانشر» (ترفع الرقم تلقائيًا). العميل يشوف «يتوفر تحديث» ويضغط تحديث
    (lis.db و uploads و backups ما تتأثر، وتنأخذ نسخة من القاعدة قبل التحديث).
 4) عند العميل (بعد التحديث): لوحة المصمم ← 📦 حزمة الإعدادات ← استيراد ← اختر الملف ← استيراد.
    على جهازه (فيه زيارات) يتم دمج: الإعدادات والتصاميم، أطباء المختبر والشهادات (بالاسم)، الأختام والتواقيع (بالتسمية)،
    تصاميم التقارير لكل تحليل (برمز التحليل). لا يتغير عنده: التحاليل والأسعار والمديات والأطباء المرسلين والمرضى.
    (بديل بدون دخول على جهازه: القسم 3 «إرسال عن بُعد» بمعرّف جهازه).
إذا لازم Setup جديد: (أ) خذ منه نسخة من lis.db و static/uploads أول، (ب) نصّب على جهاز تجريبي وتأكد أن بياناته ما انمسحت،
 (ج) بعد التنصيب استورد حزمة الإعدادات (على قاعدة جديدة يُستورد كل شي حتى الكتالوج).

## و) تصحيح بعد قراءة client_builder.py (بناء الـSetup)
- «تجهيز ملف تنصيب العميل» (/designer/client-builder) يستخدم مجلد البرنامج نفسه كنسخة العميل (this folder IS the client's copy):
  1) يحفظ اسم المختبر (عربي/إنكليزي) والهاتف والعنوان ورابط البوابة والمفتاح بقاعدة هذا المجلد.
  2) اختياري: ينشئ بوابة Cloudflare للعميل تلقائيًا (node scripts\new-client.mjs <slug> بمجلد مشروع البوابة، ويقرأ الرابط والمفتاح من
     clients\<slug>\INFO.txt ويخزنهما). مرة وحدة قبلها: افتح cmd واكتب  npx wrangler login
  3) tools\make_client_installer.py: ينسخ lis.db وينظّفها (يمسح المرضى والزيارات، يضع دخول مصمم عشوائي، كلمة سر admin التي تكتبها، يعطّل مستخدمي الديمو).
  4) build_client.bat: PyInstaller ثم Inno Setup ← installer_output\LabSystem_Setup.exe.
- معناها: الـSetup يحمل كل إعداداتك (أطباء، شهادات، أختام، تقارير، باركودات، شعار، كتالوج، اسم/هاتف/عنوان المختبر) لأنها داخل قاعدة بياناتك،
  لكن بدون أي مرضى. لذلك لعميل جديد ما تحتاج حزمة الإعدادات أصلًا، والخطوات اليدوية لـCloudflare بالقسم (د/3) هي البديل فقط إذا ما تستخدم الإنشاء التلقائي.
- تحذير: الخطوة (1) تغيّر اسم/هاتف/عنوان المختبر بقاعدة مجلدك نفسه. إذا تبني لأكثر من عميل، ابنِ من نسخة منفصلة من المجلد لكل عميل.
- ما لا أعرفه (ملفات ما وصلتني: installer_client.iss / build_client.bat / make_client_installer.py): كيف يتصرف مثبّت Inno لو لقى برنامج قديم
  وقاعدة lis.db موجودة (يستبدلها أو يبقيها). الـSetup يحمل قاعدة نظيفة بلا مرضى، فلو استبدلها ضاعت بيانات العميل الحالي.
- لذلك: عميل جديد = Setup. عميل عنده مرضى = تحديث داخل البرنامج + حزمة الإعدادات (القسم هـ).
